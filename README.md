# 买星是真的，热榜基本没被买穿 —— 但从 2026 年起，没人能再核查了

👉 **[打开页面](https://nelzomal.github.io/github-stars/)**

「热门项目是不是都在买星？」

有人认真数过：**600 万颗**星标被判定为假，分布在 **26,254** 个仓库上。
但把分母换成「实际出现在 GitHub 热榜上的仓库」，被渗透的比例月度峰值只有 **1.29%**。
两个数字都对，方向相反 —— 买星是产业规模，热榜的排序算法却把绝大部分刷出来的热度挡在了外面。

前半部分的数据来自 ICSE'26 论文的公开复现包，本页用标准库重算了一遍以校验管线；
**这些仓库和账号今天还剩多少、热榜的分母、以及两条核查通道的现状**，是 2026-08-18 现场测的。

## 结论

```
5,999,002  颗星标被判定为假（2019-07 → 2024-12）
   26,254  个仓库身上带着这些假星
   18,617  …其中够得上「一次刷星行动」的 ........... 70.9%
   17,277  …今天已经从 GitHub 上消失了 ............. 92.8%
    5,187  （同月份、未被标记的对照组消失了这么多） 34.8%
       80  …上过 GitHub 热榜的 ..................... 0.43%
```

横向的 0.43%（刷星仓库里有多少上过热榜）论文报过。
纵向的比例 —— **热榜仓库里有多少在刷星** —— 论文没给，这里补上：

| 月份 | 热榜仓库 | 其中在刷星 | 占比 |
|---|---:|---:|---:|
| 2024-03 | 1,905 | 21 | 1.10% |
| 2024-05 | 1,939 | 25 | **1.29%** |
| 2024-07 | 1,459 | 5 | 0.34% |
| 2024-10 | 1,489 | 10 | 0.67% |
| 2025-01 | 1,474 | 6 | 0.41% |

上过热榜的那 80 个里，**AI / 大模型占 26 个（32.5%）** —— 是所有类别里最高的。
刷星仓库整体的画像完全不同：能从仓库名认出类别的那 56%（其余 44% 名字看不出来）里，
最大的三块是盗版软件破解（4,240）、游戏外挂与脚本执行器（2,334）、
Telegram 薅羊毛点击器（1,275）。换句话说，能混上热榜的刷星项目，和其余那一万多个不是一类东西。

## 检测器可信吗

这套判定是启发式的，没有真值。唯一的外部验证是让 GitHub 自己投票 ——
把 18,617 个被标记的仓库和一组**同月份、同样拿到过 ≥50 星、但没被标记**的仓库
一起拿去查今天还在不在：

| | 仓库数 | 今天已消失 |
|---|---:|---:|
| 被判定刷星 | 18,617 | **92.8%**（17,277） |
| 同月份对照组 | 14,908 | 34.8%（5,187） |

2.7 倍的差距。GitHub 不知道这份名单的存在，是它自己按自己的规则把这些仓库删掉的。

对照组的构造写在 `2_survival.py` 里：从「当月拿到过 ≥50 星」的全部仓库中，
剔除检测器碰过的每一个，再**按被标记仓库的刷星月份逐个配对**抽取 ——
不配对的话，2019 年的仓库比 2024 年的多六年时间可以消失，那部分差距会被算到检测器头上。
有 3,709 个被标记仓库在自己那个月里已经找不到未被标记的同类，所以对照组是 14,908 而非 18,617。

论文在 2025-01 用**另一种基线**测得刷星仓库 90.42% 已删、基线 5.03%；
那个 5.03% 的分母和这里不同，两个对照数不可直接比较。可比的是刷星组本身：
90.42% → 92.8%，19 个月里又高了两个百分点。

## GitHub 清掉的到底是谁

仓库被删可以是因为它装的东西，不一定是因为星。所以把同一个问题往下问一层，问到**账号**：
取 2024-07-16 三个整点（3、11、19 时）的 GH Archive，
把那几小时里的每一个星标账号按「点没点过被标记的仓库」分成两组，再逐个查今天还在不在。

| 组 | 数量 | 今天已消失 |
|---|---:|---:|
| 被判定刷星的仓库 | 18,617 | **92.80%** |
| 同月份对照组（仓库） | 14,908 | 34.79% |
| 点过被标记仓库的账号 | 696 | **47.70%** |
| 同小时对照组（账号） | 2,000 | 8.15% |

账号这一组是**故意做弱的**：那几小时里点过任一被标记仓库的人全算进来了，包含大量正常用户。
论文用后处理过的账号集在 2025-01 测得 57.07% 已删（基线 3.54%）—— 稀释只会让差距变小，是安全的方向。
口径上，GraphQL 对**已删除、已封禁、已改名**一律返回 null，三者从外部分不开；
组织账号不能点星，所以 null 不会是组织。

**但被清掉的不是「星得多」的账号，恰恰相反。**两组幸存者各自星过多少个仓库：

| 星过的仓库数 | 0 | 1 | 2–9 | 10–99 | 100–999 | 1k–9999 | 10k+ |
|---|---:|---:|---:|---:|---:|---:|---:|
| 刷星组（364 个幸存） | 8.8% | 18.1% | 35.2% | 24.5% | 10.4% | 3.0% | 0.0% |
| 对照组（1,837 个幸存） | 3.2% | 3.1% | 9.6% | 29.0% | 41.6% | 13.0% | 0.5% |

中位数：刷星组 9 个，对照组 138 个。
对照组里星得最多的那个账号星过 **49,919** 个仓库，活得好好的。

GitHub 的 [Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)
确实禁止「rank abuse, such as automated starring or following」和为传播虚假互动而建立的二级市场，
但**星标总数没有上限** —— 文档里没有这个数字，能卡住你的只有
[二级限流](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)：
每分钟 80 次、每小时 500 次内容生成请求，且网页上的点击也计入。
被清掉的是另一种账号：没有仓库、只点过一两颗星的空壳。

**仓库那一侧，删的理由几乎也不是星。**按类别拆开：

| 类别 | 仓库数 | 今天已消失 |
|---|---:|---:|
| 未分类 | 8,262 | 90.8% |
| 盗版软件 / 破解 | 4,240 | 99.4% |
| 游戏外挂 / 脚本执行器 | 2,334 | 98.9% |
| 薅羊毛 / 自动点击 | 1,275 | 99.5% |
| 机器人 / 账号工具 | 1,232 | 95.8% |
| 加密货币 | 590 | 95.3% |
| AI / 大模型 | 201 | 41.8% |
| 垃圾 / 钓鱼 | 131 | 86.3% |

被删掉的是恶意软件、盗版分发、外挂加载器 —— 星标是它们的**广告手段**，
GitHub 下架的是载荷，星只是跟着一起没了。
**只买星、内容本身没问题的仓库基本不会被动**：80 个上过热榜的被标记仓库里，
**60 个（75%）今天还在线**，而整体是 92.8% 已删。

## 而现在，这套核查做不了了

上面每个数字追到底都依赖两样东西：**谁点的星**，和**什么时候点的**。
过去有两条公开通道能拿到，2026-08-18 我把两条都测了一遍：

**通道一：星标名单。已被官方关闭。**

```
GET /repos/{owner}/{repo}/stargazers   未登录 → 401 Requires authentication
                                       已登录 → 404 Not Found
github.com/{owner}/{repo}/stargazers          → 404
GraphQL stargazers(orderBy: STARRED_AT)       → 整个查询报错，0 条
```

GitHub 2026-06-30 公告：该接口只对仓库管理员和协作者开放，理由是这些数据
「被越来越多地用于收集用户信息以实施垃圾行为」。对其他人返回「找不到」而不是「无权限」。

**通道二：GH Archive。在没有公告的情况下烂掉了。**

GH Archive 逐小时存档 GitHub 公开事件流，星标事件在里面叫 `WatchEvent`，
所有假星研究都建在它上面。每月抽一天、每天抽三个整点、各读前 4 MB：

| | WatchEvent 占比 | ForkEvent | PushEvent |
|---|---:|---:|---:|
| 2019-07 | 8.62% | 3.42% | 52.9% |
| 2025-08 | 3.04% | 0.72% | 67.2% |
| 2026-01 | 3.00% | 0.55% | 68.9% |
| 2026-02 | 1.62% | 0.28% | 69.5% |
| 2026-06 | 0.16% | 0.04% | 85.1% |
| 2026-07 | **0.06%** | 0.02% | 90.9% |

同期 `PushEvent` 的绝对量不降反升 —— 存档本身在正常工作，塌掉的只有星标、fork、issue。

**但 GitHub 自己还在发星标事件。** 同一时刻拉官方公开事件时间线 `GET /events`：
299 条事件里有 23 条 `WatchEvent`（7.7%），和 2019 年的比例没区别。
所以不是 GitHub 停发，是采集端不再收到。存档方自己也在追这个问题
（[#320](https://github.com/igrigorik/gharchive.org/issues/320) 测出捕获率从 95–100% 掉到不足 20%，
拐点在 2025-06 和 2026-02，和上表一致；
[#310](https://github.com/igrigorik/gharchive.org/issues/310)「事件掉了 100 倍」）。

值得记一笔：#320 用来当基准的接口正是 `/stargazers` —— 写下那份分析**六周之后**，
GitHub 把它关掉了。用来发现后者坏了的手段，恰好是前者。

## 那现在还能看什么

星标名单没了，仓库的其它计数还在。抓了热榜的全语言首页 + 19 个语言榜 × 日/周/月三档，
去重 **731** 个仓库，逐个查这些比值：`fork:star`、`星数/贡献者`、
`星数/提交数`、`星数/仓库年龄`。

**这不是一份嫌疑名单。** 按 `fork:star` 升序排最前面的几乎全是口碑很好的正经项目 ——
安全扫描器、Neovim 插件、终端工具。原因很朴素：这类东西是拿来装的，不是拿来改的。
同样地，一个真正火起来的新项目，开头几周必然贡献者少、fork 少、提交少。

这些数字只能**反过来**用：星数很高、而这几项全部贴地、issue 区没人说话、提交只有几十条 ——
那值得多看两眼，也仅仅是多看两眼。星标名单没了之后，剩下的就只有这种程度的判断了。

## 查一个具体的仓库

```bash
python3 scripts/probe_repo.py owner/repo [owner/repo ...]
```

两个熬过 2026 年封锁的接口拼出来的一个简易版：`/repos/{o}/{r}/events`
还能吐最近的 WatchEvent（带账号和时间戳），GraphQL 的
`user.starredRepositories.totalCount` 还能回答「这个账号一共星过几个仓库」——
后者正是低活跃签名要问的问题。

**它不是那个检测器**：事件接口封顶 300 条事件，对一个每天涨百来颗星的仓库只有一两天的窗口，
而且只能看到**最近**的星，去年刷的完全看不见；同步刷星（lockstep）签名需要全局的
账号×仓库二部图，今天的公开数据里根本不存在，跑不了。
所以一次传几个仓库、横着比列，单看一个数没有意义。

实测一例（2026-08-18）：

| 仓库 | 样本 | 只星过 1 个 | 0 仓库 | 0 粉丝 | 四项全空 | 账号年龄中位 |
|---|---:|---:|---:|---:|---:|---:|
| unclecode/crawl4ai | 153 | 3.9% | 21.6% | 38.6% | 0.0% | 1,257 天 |
| browser-use/browser-use | 87 | 2.3% | 20.7% | 39.1% | 1.1% | 1,250 天 |
| langchain-ai/langchain | 44 | 4.5% | 27.3% | 36.4% | 0.0% | 1,734 天 |
| ollama/ollama | 136 | 1.5% | 29.4% | 52.9% | 1.5% | 984 天 |

注意 ollama 那一行：0 粉丝 52.9%、新号 19.9%，都比前两个高，而它显然不是刷出来的 ——
一个真正主流的工具会把大量刚注册的新人带进来。**这些比例单独拿出来什么也说明不了。**

## 关于点名

页面只写出**已经被 GitHub 删除**的仓库名。
这套检测的**精度无法直接评估** —— 没法验证单独一颗星是不是买来的，论文自己也这么说，
它退而用删除率做旁证。按论文里「即便有 99% 精度」的估法，一万八千多个里仍剩约 **180 个误判**，
而这个页面没法向被误判的、还活着的项目解释什么。
（召回率论文测过：对已知恶意刷星活动是 81.23% 的仓库、75.95% 的账号。）
还在线的仓库只保留类别和数字，名字用编号代替。已删除的仓库不存在这个问题 ——
而它们恰好就是恶意软件集中的地方。

「假星」始终指*被这套启发式判定为可疑*，**不等于仓库主人买过星**：
刷星账号也会去点正常项目的星来伪装自己。

## 怎么复现

```bash
bash scripts/run.sh
```

需要先 `gh auth login`。全程约一小时，绝大部分时间花在第 2 步的三万多次仓库查询上，
以及等 GraphQL 配额。第 2、3 步都有断点续跑。

| 步骤 | 产出 | 做什么 |
|---|---|---|
| `1_reference.py` | `data/reference.json` | 拉 StarScout 复现包，用标准库重算仓库/月份口径 |
| `2_survival.py` | `data/survival.json` | 被标记仓库 + 同月份对照组今天还在不在 |
| `3_accounts.py` | `data/accounts.json` | 星标账号今天还在不在（刷星组 vs 同小时对照组） |
| `4_blackout.py` | `data/blackout.json` | GH Archive 逐月事件构成 + 四项活体接口探测 |
| `5_trending_now.py` | `data/trending_now.json` | 今日热榜 × 还能查的比值 |
| `6_trending_hist.py` | `data/trending_hist.json` | 热榜归档交叉引用，两个方向的比例 |
| `7_build.py` | `data/site_data.json` | 分类、隐名规则、火焰图层级 |
| `8_render.py` | `index.html` | 数据内联进单文件页面 |

`scripts/analysis/report.py` 会把本 README 里每个数字重算一遍 —— 出现在这里而不在那里的数字，就是没有出处。
`scripts/test_render.py` 用 headless Chrome 驱动火焰图下钻、两张表的排序筛选、月份网格和两张折线图，
验证交互没坏，并检查「在线仓库全部隐名、已删除仓库全部具名」这条规则确实成立。

`data/` 不入库：它一半是复现包的缓存，一半是活体网络的快照，重跑必然和 `index.html` 里那一份不同。

## 数据来源

历史部分来自 [hehao98/StarScout](https://github.com/hehao98/StarScout)，即
He, Yang, Burckhardt, Kapravelos, Vasilescu, Kästner，
*Six Million (Suspected) Fake Stars on GitHub: A Growing Spiral of Popularity Contests, Spam, and Malware*，
ICSE'26，[10.1145/3744916.3764531](https://doi.org/10.1145/3744916.3764531)。
本页独立复算出该论文的 18,617、5,999,002、78、以及 2024-07 峰值 16.66% 四个数，作为管线正确性的校验。

热榜历史来自 [larsbijl/trending_archive](https://github.com/larsbijl/trending_archive)，
3,283 天，2017-03-23 → 2026-08-17，覆盖 cpp / go / javascript / python / rust / typescript 六个语言榜
（不含全语言首页，所以分母偏小）。

检测窗口在 2024-12 结束 —— 页面上 2025 年之后热榜占比的下降**不是真的下降**，
是那之后没有任何仓库被检测过。
